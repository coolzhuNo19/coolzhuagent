# MCP 插件预装调试方案 — 总纲

> 日期：2026-06-06
> 适用：coolzhu code agent（modules/tooling 插件系统 + web-console）
> 目标：为多类生产力软件**预装 + 调试** MCP（Model Context Protocol）能力，分类别给出落地方案。
> 分类文档见同目录 `01`~`09`。

## 一、工程现状（事实）

- **插件系统**（`modules/tooling/packages/plugin-system/src/lib.rs`）：插件由 manifest 描述
  `command + args + env`，运行时 `Command::new(command).args(args)` 以 **stdio 管道**拉起子进程
  （lib.rs:299，stdin/stdout/stderr piped），注入 `CLAW_PLUGIN_ID/NAME/TOOL_NAME/TOOL_INPUT/PLUGIN_ROOT` 等环境变量。
- **bundled 预置目录**：`CARGO_MANIFEST_DIR/bundled`（lib.rs:911），可放随包分发的插件。
- **安装接口**：`api_plugins_install`（main.rs:8455）当前为 **P1：本地源加载即用**
  （plugin_source_roots / skills 目录），P2 才接"远程 marketplace 拉取到 scope 目录"。
- **工具注册**：`modules/tooling/packages/tool-registry`；命令路由 `command-router`。
- **子进程编码**：tool-registry 已有 `decode_console_output`（UTF-8→GB18030 回退），子进程输出须走它防中文乱码。

### 关键缺口
工程**尚无标准 MCP 客户端**（JSON-RPC over stdio / HTTP-SSE）。而生态里几乎所有目标 MCP server
都是 `npx -y <pkg>` / `uvx <pkg>` / `python -m <pkg>` 的 **stdio MCP**，或远程 **HTTP（custom connector）**。
要"预装"它们，必须先解决 MCP 接入层。

## 二、总体架构（两条落地路径）

- **路径 A（推荐，通用）— 内置 MCP 客户端桥（MCP Host）**
  在 coolzhu 内新增一个 MCP 客户端：按配置启动/连接 MCP server（stdio 或 HTTP），完成
  `initialize → tools/list`，把远端工具**映射进 tool-registry**，`tools/call` 时转发并回传结果。
  子进程输出统一走 `decode_console_output`。这是一次性投入、服务所有类别的正解。
- **路径 B（过渡）— 包成本项目 plugin manifest**
  对单个简单 server，写一份 manifest（`command=npx/uvx ...`）借现有 stdio 管道直接跑，
  适合快速验证或一次性工具，不具备完整 MCP 协商能力。

> 建议：先按路径 B 打通 1–2 个高成熟度 server（如 Obsidian、Blender）验证端到端，
> 再投入路径 A 的 MCP Host 做统一接入。

## 三、预装 + 调试统一流程（每类通用）

1. **依赖准备**：Node(npx) / Python(uv/uvx) 运行时；对应**宿主软件**及其 REST/RPC 插件（如 Obsidian Local REST API、KiCad 9+、Blender addon）。
2. **注册配置**：`mcp_servers.json`（`command/args/env/transport/scope`），预置到 `bundled` 或 scope 目录。
3. **连接自检**：`initialize` + `tools/list`，打印工具清单与数量（首个验收点）。
4. **冒烟用例**：每类挑 1–2 个**只读**工具跑通（不产生副作用）。
5. **写操作授权**：写/破坏性工具默认 `execute=false` + 二次确认，对接**三档授权**。
6. **日志与编码**：子进程输出走 `decode_console_output`，中间产物落 `tmp/`。

## 四、安全基线（强制）

- API Key（金融数据、视频生成等）走**环境变量/本地配置**，不硬编码、不入 URL query、不外传。
- 远程 HTTP MCP（custom connector）需密钥管理与来源校验；只连用户/我方指定 URL。
- 写/破坏性工具默认 `execute=false` + 二次确认；对接三档授权（workspace 内 / 指定目录 / full access）。
- 宿主软件的自动化会操作真实工程文件/设备，预装阶段一律先在**示例工程/沙箱**验证。
- `:8765` 若远程暴露须加鉴权（token/配对码），穿透优先私有 VPN。

## 六、里程碑

- **M1**：路径 B 打通 Obsidian + Blender 两个 server（端到端冒烟）。
- **M2**：实现路径 A 的 MCP Host（stdio + HTTP），统一 `tools/list`→注册→`tools/call`。
- **M3**：按类别批量预置 `mcp_servers.json` + bundled，补三档授权与冒烟用例。
- **M4**：远程 marketplace 安装（对接 `api_plugins_install` 的 P2）、可观测面板（连接状态/工具数/最近调用）。

## 七、架构落地状态（2026-06-09 实施）

**路径 A（MCP Host）已落地** —— `modules/gui-web/packages/web-console/src/main.rs`：

- **协议**：JSON-RPC 2.0 over stdio（newline-delimited），`initialize → notifications/initialized → tools/list → tools/call`，
  protocolVersion `2025-06-18`，clientInfo `coolzhu-mcp-host/0.1.0`。
- **配置**：内置 `DEFAULT_MCP_SERVERS_JSON` 预装清单（10 条 = 00 验证 + 01~09 各类代表）；
  workspace `.coolzhu/mcp_servers.json` 存在则整体覆盖（用户可改 command/env/enabled）。
  依赖宿主软件/API Key 的条目预置 `enabled=false`，宿主就绪后开启。
- **运行时**：`McpRuntime`（tokio 子进程 + stdin 管道 + stdout 行读 task + stderr→diag），
  全局 `mcp_runtimes()`（tokio Mutex<HashMap>）；请求-响应按 id 匹配、45s 超时；
  Windows 下 `cmd /c npx -y <pkg>` 拉起（npx.cmd 解析），CREATE_NO_WINDOW。
- **API**：
  - `GET  /api/mcp/servers` — 清单 + connected/tool_count
  - `POST /api/mcp/servers/{id}/connect` — 握手 + 工具清单（重复 connect 自动替换旧进程）
  - `POST /api/mcp/servers/{id}/disconnect`
  - `POST /api/mcp/call` — {server_id, tool, arguments} 转发 tools/call
- **验收实测**：
  - `mcp-everything`（官方参考 server 2.0.0）：connect 10.4s（含 npx 首次拉包）→ **13 工具**；
    `tools/call echo` → 2ms 返回 "Echo: coolzhu MCP Host online"。**协议全链路 ✓**
  - `godot-mcp`（02 游戏开发类，npm godot-mcp@0.1.0）：connect 6.4s → **14 工具**
    （launch_editor/run_project/create_scene/add_node/load_sprite/save_scene/get_godot_version/list_projects…）；
    `get_godot_version` 如实报"未找到 Godot.exe"并给出解决建议——连接自检与调用链路 ✓，引擎依赖如实暴露。

**后续（按里程碑）**：M2 HTTP transport + 工具映射进 tool-registry（暴露给 LLM 须过三档授权）；
M3 各类宿主软件就绪后逐条开启并冒烟；M4 marketplace 安装 + 可观测面板。
