# 定时任务（Scheduled Tasks）完成度分析 — 闹钟模型差距

> 日期：2026-06-06
> 范围：`modules/gui-web/packages/web-console`（main.rs + app.js）
> 目标模型澄清：用户要的不是"固定时长任务"，而是**类似闹钟的固定时间触发任务**
> （例：每天上午 10:00 总结 Top10 实时新闻热度）。

## 一、现状盘点（代码事实）

### 1. 数据结构
`ConfigScheduledTask`（main.rs ≈3537）字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | String | 任务 ID |
| `target_session_id` | String | 投递目标会话 |
| `content` | String | 触发时写入会话的内容（即"指令"） |
| `run_at_ms` | u64 | **绝对** epoch 毫秒触发时刻 |
| `interval_ms` | Option<u64> | 重复间隔（≥60_000），`None` = 单次 |
| `permissions` | Vec<String> | 权限标记 |
| `status` | String | `scheduled` / `executed` / `failed` |
| `created_at_ms` / `last_run_at_ms` / `last_error` | — | 审计字段 |

### 2. CRUD + 执行（已实现）
- `api_create_task_schedule`（≈4519）、`api_delete_task_schedule`（≈4580）、列表、`api_run_due_task_schedules`（4613）。
- 到期判定：`status=="scheduled" && run_at_ms <= now`。
- 执行后重排：有 `interval_ms` → `run_at_ms = now + interval_ms`、`status` 回 `scheduled`；否则 `status="executed"`。
- `deliver_scheduled_task`（4664）：**仅向目标会话 append 一条 chat 消息**（author=`Scheduler`，role=`user`，kind=`scheduled-task`）；会话不存在则 `NOT_FOUND`。

### 3. 触发入口（关键）
- 路由：`POST /api/task-schedules/run-due`（main.rs:654）。
- 前端：`taskScheduleRunDue`（app.js:2035）**绑定在按钮点击**（`task-schedule-run-due`，app.js:332），**不是 setInterval 轮询**。
- 全仓 `tokio::spawn` 仅 `spawn_showui_exit_monitor`（361，监控 ShowUI 进程）等少数，**没有任何定时任务后台调度器**。

## 二、与"闹钟模型"的差距（致命 → 次要）

1. **❌ 无自动触发（致命）**：到期任务只有在**人工点击"运行到期"或外部打 POST** 时才执行。
   关掉控制台页面/无人值守时，"每天 10 点"永远不会自己响。闹钟的本质能力缺失。
2. **❌ 无挂钟/cron 表达式**：只有 `run_at_ms`（绝对时刻）+ `interval_ms`（固定毫秒间隔）。
   - "每天 10 点"需手动算下一个 10:00 的 epoch + `interval=86_400_000`。
   - 无法表达"工作日 9 点""每周一""每月 1 号"。
3. **⚠️ 周期漂移**：重排用 `now + interval_ms`，`now` 是**实际执行时刻**而非计划时刻。
   一旦执行延迟（或人工补点），每天会逐步偏离整点，越跑越歪。正确做法应按**计划时刻对齐**或按挂钟重算下一个整点。
4. **⚠️ 时区 / 夏令时**：`run_at_ms` 是 UTC epoch；"每天 10 点"须按**本地时区**计算，跨 DST 会偏 1 小时。
5. **⚠️ 错过补偿（misfire）缺失**：关机期间错过的触发无策略（补跑 / 跳过 / 仅跑最近一次）。
   当前逻辑下，长时间未运行 + 单次 run-due 只投递一次，再对齐到 `now+interval`，行为不可预期。
6. **⚠️ 投递 ≠ 执行**：`deliver_scheduled_task` 只写入一条 user 消息，**不保证 agent 真正运行并产出**。
   "每天 10 点总结新闻"要落地，须确认目标会话/Goal 链路会**自动消费**这条消息并产出结果。
7. **⚠️ 无运行态 / 重入保护 / 重试**：缺 `running` 状态；长任务跨触发点无保护；失败仅记 `last_error`，无重试/退避/通知升级。

## 三、完成度评分

| 维度 | 状态 |
| --- | --- |
| 数据模型 / CRUD | ✅ 完整 |
| 单次绝对时间触发（语义） | ✅ 可表达 |
| 固定毫秒周期（语义） | ✅ 可表达 |
| **自动触发（后台调度器）** | ❌ 缺失 |
| **挂钟/cron 表达式** | ❌ 缺失 |
| 时区 / DST | ❌ 缺失 |
| misfire 补偿 | ❌ 缺失 |
| 投递后自动执行产出 | ⚠️ 未串通 |
| 运行态/重试/通知 | ❌ 缺失 |

**结论**：CRUD 与数据底座可用，但作为"闹钟"**不可用**——核心缺"自动触发 + 挂钟计划"。

## 四、增强路线（建议落地顺序）

- **A. 后台调度器（最高优先）**：`main()` 内 `tokio::spawn` 每 30s tick，调用与 run-due 等价的共享函数（先把 4613 的核心逻辑抽成 `run_due_task_schedules_once()` 供路由与后台复用），不依赖前端页面是否打开。
- **B. 挂钟计划模型**：`ConfigScheduledTask` 增 `schedule_kind`（`once`/`interval`/`daily`/`weekly`/`monthly`/`cron`）+ `wall_clock`（`HH:MM` 及星期/日）或 `cron_expr` + `timezone`。
  `next_fire` 基于**本地挂钟重算并对齐整点**，替代 `now+interval` 漂移（可引入 `chrono` + `cron` crate）。
- **C. misfire 策略**：新增字段（`skip` / `fire_once` / `backfill` + 补跑上限），重启后按策略处理错过项。
- **D. 运行态与可靠性**：`running` 状态 + 重入保护；失败重试次数/指数退避；目标会话缺失/失败的通知。
- **E. 投递即执行**：投递消息后触发会话自动运行（或 Goal commander 入口），确保产出而非仅留言。
- **F. 前端**：计划编辑器支持"每天 / 每周 / 工作日 + HH:MM"，展示 `next_fire`、上次结果、错过提示；去掉对"手动运行到期"按钮的依赖（保留为调试入口）。

## 五、最小可用闭环（MVP 建议）

1. 后台 30s tick 调度器（A）。
2. `daily HH:MM` + `weekly` 两种挂钟计划（B 的子集），本地时区对齐。
3. misfire = `fire_once`（错过只补最近一次）（C 简化）。
4. 投递后触发目标会话自动应答（E）。

> 满足 4 项即可支撑"每天上午 10 点总结 Top10 实时新闻"这一验收场景。
